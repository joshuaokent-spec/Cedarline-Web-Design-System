Cedarline Web Design System

One shared language for calm, trustworthy insurance experiences.

A reusable set of visual, interaction, accessibility, and content standards designed to keep Cedarline customer and employee experiences consistent without making every interface look identical.

01

Calm under pressure

Insurance interactions often happen during stressful moments. Components should reduce uncertainty, not amplify it.

02

Plain language first

Formal insurance terms remain available, but the interface should help people reach them without already knowing the vocabulary.

03

Accessible by default

Focus, contrast, semantics, error recovery, motion, touch targets, and reflow are baseline requirements.

04

System, not sameness

Shared tokens and components create consistency while still allowing consumer and enterprise products to use different densities.

Foundation

Color

Brand colors establish recognition; semantic colors communicate state. Components reference semantic tokens rather than hard-coded color names.

Use

Cedar green for primary actions, navigation emphasis, and brand recognition.

Avoid

Using color alone to communicate priority, errors, selection, or success.

Foundation

Typography

A system-ui stack keeps the prototype fast and portable. Scale, weight, spacing, and hierarchy matter more than relying on a proprietary font.

Component

Buttons

Use one clear primary action per decision point. Secondary and tertiary actions should support—not compete with—the primary path.

Do

Use labels that describe the outcome: “Submit claim report” or “Save progress.”

Don’t

Use vague labels such as “Yes,” “OK,” or “Continue” when the action has a specific consequence.

Dialog

Standard

Accessibility

Accessibility requirements belong in component definitions—not in a cleanup checklist after visual design is finished.

Keyboard

Every interactive component must work without a pointer and expose visible focus.

Semantics

Prefer native HTML controls and preserve meaningful headings, labels, landmarks, and group relationships.

Error recovery

Identify the specific problem in text, associate it with the control, and explain how to correct it when known.

Motion

Honor reduced-motion preferences and avoid unnecessary animated movement.

Reflow

Layouts must remain usable at narrow widths and high zoom without hiding essential content.

Color

Contrast must be validated, and meaning must never depend on color alone.

Standard

Content & voice

Cedarline copy should be direct, calm, human, and precise—especially when the user may be stressed.

Preferred

What happened?
Choose the option that fits best. You can clarify details later.

Avoid

Select loss classification.
Please choose the applicable loss type from the choices below.

Use verbs for actions. “Upload documents,” not “Document upload.”

State what can wait. “You can add photos later.”

Avoid false certainty. “Report received” is not “Coverage approved.”

Translate before defining. Plain language should lead users toward formal insurance terminology.

Standard

Responsive behavior

Responsive design changes layout and density without changing the underlying task model.

Compact< 640px

Single-column tasks, stacked choices, large touch targets.

Medium640–960px

Flexible grids, simplified navigation, detail regions may stack.

Wide> 960px

Contextual side panels, multi-column foundations, enterprise density where appropriate.

Standard

Governance & handoff

A design system only works if teams know when to reuse, extend, or challenge it.

Reuse first

Use an existing component when the user need and interaction model already match.

Extend with evidence

Add variants when a recurring, documented need cannot be met by an existing pattern.

Accessibility is a gate

A component is not complete until keyboard, semantics, focus, contrast, error, motion, and reflow behavior are documented.

Document decisions

Component docs should include purpose, when to use, when not to use, anatomy, states, accessibility, and implementation notes.

From portfolio project to production system

A real enterprise design system would add product-team research, contribution workflows, versioning, coded packages, design-tool libraries, analytics, accessibility audits, and named governance owners.
